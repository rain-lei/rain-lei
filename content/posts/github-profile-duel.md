# GitHub 主页对决：落后 29 分之后

![GitHub 主页对决结果：@hyhyhyyyy 对阵 @rain-lei](/uploads/2026/github-profile-duel.png)

一场 GitHub 主页对决把两个账号放在了一起：`@hyhyhyyyy` 得到 **64.10 分**，`@rain-lei` 得到 **35.10 分**，差距为 **29.0 分**。

页面给胜方贴上了“NPC”，给我贴上了“拉完了”。这些标签显然更像娱乐化文案，不适合作为对开发能力的正式评价。不过，页面列出的六个维度可以当作一面不太严肃的镜子，看看公开主页还有哪些可以继续建设的地方。

> 本文只依据截图整理。评分规则、数据采集范围和权重没有在截图中展示，因此不能把分数理解成 GitHub 官方排名，也不能据此评价一个人的真实技术能力。

## 对决结果

| 账号 | 总分 | 页面标签 | 结果 |
| --- | ---: | --- | --- |
| `@hyhyhyyyy` | 64.10 / 100 | NPC | 胜 |
| `@rain-lei` | 35.10 / 100 | 拉完了 | 负 |

总分只说明这套工具如何读取公开账号，不等同于代码质量、学习能力或者未来潜力。对刚开始积累项目的账号来说，仓库历史和社区互动尚少，本来就容易在此类评分里处于劣势。

## 六项维度

| 维度 | `@hyhyhyyyy` | `@rain-lei` | 差值（rain-lei - 对方） |
| --- | ---: | ---: | ---: |

`@rain-lei` 在账号成熟度和社区影响力上略高，但在原创项目、贡献质量以及生态维护上落后。其中最大的单项差距来自“生态 / 维护影响力”，它几乎解释了总分差距的一半。

## 分数真正提醒了什么

### 1. 仓库数量不等于原创项目质量

公开仓库只是起点。一个项目是否容易被理解，还取决于 README、运行截图、安装步骤、版本记录、问题列表和后续迭代。如果仓库只有代码，没有项目背景和使用说明，外部工具和真实访客都很难判断它解决了什么问题。

对我来说，比继续创建很多练习仓库更重要的是，把现有项目补完整：明确目标、整理目录、增加演示、记录决策，并留下能够复现的运行方式。

### 2. 贡献质量需要持续记录

一次提交只能证明代码发生了变化，持续且清晰的提交历史才能说明项目如何成长。提交信息、Pull Request、Issue、测试和发布记录，都是公开贡献的一部分。

接下来应该减少含义模糊的提交，把一次改动拆成可以解释、可以检查、可以回滚的单元。相比制造提交数量，这更接近真实的软件工程过程。

### 3. 维护影响力不是短期刷出来的

截图中最明显的是 **14.9 对 0.0**。即使不知道评分算法，也能看出这项大概重视项目被使用、持续维护或与外部协作产生联系。

这一项没有速成方法。维护文档、回应 Issue、审查 PR、发布版本、修复真实问题，时间久了才会形成可信的维护轨迹。比起为了分数刻意制造活动，更合理的做法是选一两个值得长期维护的项目持续投入。

### 4. 活跃应该来自真实工作

“活跃真实性”不是绿色方格越多越好。学习笔记、项目迭代、问题修复和协作记录自然形成的提交，才具有可读性。为了填满贡献图而提交空改动，既不能改善项目，也会让历史变得混乱。

## 下一阶段怎么做

这次对决可以转化成一份简单的行动清单：

1. 选择一个主项目，持续维护而不是频繁开新坑。
2. 补齐 README、演示图片、安装步骤和功能边界。
3. 为重要改动使用 Issue 和 Pull Request 留下决策过程。
4. 增加最基本的测试、自动构建和发布记录。
5. 参与真实的开源协作，从小型文档修正和问题复现开始。
6. 定期整理个人主页，让代表项目比提交数量更醒目。

## 最后

35.10 分当然不高，“拉完了”也确实很有节目效果。但账号仍处在积累阶段，这张图更像一次阶段性快照，而不是结论。

真正值得比较的不是今天和别人差多少分，而是几个月以后，仓库是否比现在更完整，代码是否更容易理解，项目是否真的帮助到了别人。等积累到下一个阶段，再回来打一场。
